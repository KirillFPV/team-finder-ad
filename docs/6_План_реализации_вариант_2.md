## Решения по расхождениям в условии

1. `User.skills` — **ManyToMany** к `Skill` с `related_name="users"`. В рекомендациях написано ForeignKey, но пользователь должен иметь несколько навыков, а шаблон вызывает `user.skills.all`.
2. Основной адрес списка проектов — `/projects/list/`: его используют шаблоны. Для упомянутого в тексте `/project/list/` сделать перенаправление. Все ссылки и POST-запросы привести к завершающему `/`, чтобы POST не зависел от редиректа `APPEND_SLASH`.
3. Пользователей сортировать от новых к старым (`-date_joined`, `-pk`), как в функциональном описании и чек-листе; проекты — `-created_at`, `-pk`.
4. Списки передают `page_obj` и `query_prefix`, необходимые реальным шаблонам; дополнительно сохранить имена контекста `projects` и `participants` из рекомендаций.
5. Добавление навыка возвращает поля из условия `skill_id`, `created`, `added` и дополнительно `id`, `name`, которые читает `skills.js`.
6. При регистрации обязательны только имя, фамилия, email и пароль. Телефон хранить пустым как `NULL`, а заполненный номер нормализовать в `+7XXXXXXXXXX` и проверять на уникальность. Аватар генерировать автоматически. Это устраняет противоречие с обязательными phone/avatar в описании модели.
7. Добавить email в форму редактирования профиля: функциональное описание разрешает менять email, хотя в заготовке формы это поле отсутствует.
8. «Избранное» подробно отнесено к варианту 1; в карточках и меню варианта 2 соответствующих элементов нет. Планировать вариант 2 без избранного и фильтров варианта 1. Повторение избранного в общем описании и чек-листе зафиксировать в README как неоднозначность исходных материалов.
9. Выход перевести на POST-форму с CSRF в меню и описать отличие от предложенного в уроке GET. Изменение состояния через остальные endpoints также разрешать только методом POST.

Эти решения записать в README для ревьюера, как требует урок с рекомендациями.

## Архитектура

Достаточно двух предметных приложений: `users` и `projects`. Общую проверку GitHub-ссылок вынести в небольшой модуль `team_finder/validators.py`. Отдельный REST-фреймворк для нескольких JSON-запросов не требуется: использовать Django views и `JsonResponse`.

| Модель | Поля и связи |
| --- | --- |
| `users.User` | Наследник `AbstractUser` с удалённым `username`, идентификатором `email`, своим менеджером; `name`/`surname` по 124 символа, `avatar`, `phone` до 12 символов, `github_url`, `about` до 256 символов; стандартные поля доступа и даты |
| `users.Skill` | `name` до 124 символов; непустое название после обрезки пробелов; алфавитная сортировка; уникальность без учёта регистра, чтобы повторное создание не порождало дубликатов |
| `User.skills` | ManyToMany к `Skill`, `blank=True`, обратная связь `users` |
| `projects.Project` | `name` до 200 символов, `description`, `github_url`, `created_at`, `status` (`open`/`closed`, до 6 символов); FK `owner` с `related_name="owned_projects"`, `on_delete=CASCADE` |
| `Project.participants` | ManyToMany к `User`, `blank=True`, обратная связь `participated_projects` |

`AUTH_USER_MODEL` определить до первой миграции. Удаление пользователя удаляет его проекты и строки связей; удаление навыка из профиля удаляет только связь. Индексировать дату создания проектов и дату регистрации пользователей; уникальность email, телефона и названия навыка обеспечить на уровне БД. Для списков применять `select_related`, `prefetch_related` и при необходимости аннотацию числа участников.

## Порядок реализации

### 1. Подготовить воспроизводимый запуск

- [ ] Выбрать единое окружение Python (для начала Python 3.12), перевести `requirements.txt` в UTF-8, установить и проверить зависимости в venv.
- [ ] Создать локальный `.env`, задать `TASK_VERSION=2`; согласовать внешний порт PostgreSQL между `.env_example` и Compose.
- [ ] Настроить `ALLOWED_HOSTS`, русскую локализацию, адрес входа, статику и media; секреты брать из окружения.
- [ ] Дополнить `.gitignore`: сейчас он исключает `/team_finder/media/`, а реальная загрузка идёт в корневой `media/`.
- [ ] Проверить Docker daemon, запустить контейнер БД с volume и убедиться, что к нему можно подключиться.

Готовность: параметры согласованы, PostgreSQL доступен, зависимости устанавливаются в чистом окружении. Создание таблиц auth отложено до добавления своей модели пользователя.

### 2. Создать модели, миграции и админку

- [ ] Создать приложения `users`, `projects` и модели из таблицы выше; подключить их в настройках.
- [ ] Реализовать менеджер пользователя с `create_user`/`create_superuser`, хешированием пароля и нормализацией email.
- [ ] Генерировать PNG-аватар с первой буквой имени через Pillow до сохранения нового пользователя; использовать шрифт с поддержкой кириллицы.
- [ ] Добавить ограничения БД и миграции, применить их к PostgreSQL.
- [ ] Настроить пользовательские формы и `UserAdmin`, администрирование проектов и навыков; проверить создание пользователей, смену паролей, блокировку через `is_active` и удаление.

Готовность: создаются суперпользователь и обычные пользователи, аватары сохраняются, связи работают через ORM и админку.

### 3. Реализовать пользователей и аутентификацию

- [ ] Регистрация с четырьмя полями, проверкой email и пароля; после успеха переход на страницу входа.
- [ ] Вход по email/паролю, ошибка «Неверный имейл или пароль»; заблокированный пользователь войти не может.
- [ ] Выход через POST и смена пароля через Django-форму с сохранением текущей сессии.
- [ ] Публичный профиль с контактами, навыками и собственными проектами; стабильный URL по id.
- [ ] Редактирование только своего профиля, загрузка аватара, изменение email и проверка его уникальности.
- [ ] Валидация телефона: только `8XXXXXXXXXX` или `+7XXXXXXXXXX`, нормализация до проверки уникальности. GitHub-ссылку проверять по разобранному hostname, исключая похожие сторонние домены.
- [ ] Список пользователей с пагинацией по 12 и корректным пустым состоянием.

Готовность: полный сценарий регистрация → вход → изменение профиля → смена пароля → выход работает; чужой профиль изменить нельзя.

### 4. Реализовать проекты и участие

- [ ] Корневой адрес перенаправляет на список проектов; список отсортирован и разбит по 12 карточек.
- [ ] Детальная страница показывает автора, описание, статус, ссылку GitHub и участников.
- [ ] Создание и редактирование через общую `ProjectForm`; владельца брать из запроса, при создании автоматически включать в участников в одной транзакции.
- [ ] Редактировать и завершать проект может только его владелец; администратор управляет любым проектом через админку.
- [ ] Завершение меняет статус на `closed` и возвращает `{"status": "ok", "project_status": "closed"}`.
- [ ] Участие переключается для авторизованного пользователя с ответом `{"status": "ok", "participant": true/false}`. Владелец не может убрать себя из участников. Новое участие в закрытом проекте запретить; уже участвующему разрешить выйти.
- [ ] Проверить, что интерфейс отражает закрытие и ограничения участия, а не только серверные проверки.

Готовность: два разных пользователя создают проекты, присоединяются к чужим и выходят; подмена id не даёт управлять чужим проектом.

### 5. Реализовать вариант 2 — навыки

| Метод и адрес | Поведение |

| `GET /users/skills/?q=Py` | JSON-массив `{id, name}`: поиск по началу названия без учёта регистра, алфавитный порядок, максимум 10; фильтрация и ограничение в SQL |
| `POST /users/<id>/skills/add/` | Только владелец; JSON с `skill_id` либо `name`; добавить существующий или создать навык, вернуть `skill_id`, `id`, `name`, `created`, `added` |
| `POST /users/<id>/skills/<skill_id>/remove/` | Только владелец; проверить существование объектов и связи, удалить связь; навык остаётся в справочнике |
| `GET /users/list/?skill=Python` | Точное совпадение названия навыка; передать `all_skills`, `active_skill`, `page_obj`, `query_prefix` и `participants` |
